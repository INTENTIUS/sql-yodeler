# Working on SQL Yodeler

Rules for anyone, person or agent, who changes this repo. Building from a clone, the tests against a server, the walkthroughs and the claims are in [CONTRIBUTING.md](CONTRIBUTING.md). A coding agent setting SQL Yodeler up in another repository follows [docs/agents.md](docs/agents.md) instead.

## Git and pull requests

- Commit messages follow Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`).
- One pull request per issue, on a branch made from `origin/main`. The PR body says `Closes #N`.
- No AI attribution anywhere: no `Co-Authored-By` trailers, no "generated by" lines, in commits, PR bodies or issue comments.
- Never `git stash`. Commit work in progress on your branch instead.
- Work in a worktree at `~/checkouts/intentius/sql-yodeler-wt/<branch>`, made with `git worktree add ~/checkouts/intentius/sql-yodeler-wt/<branch> -b <branch> origin/main`.
- Pull requests are squash-merged once their local gates pass (Checks, below). Nobody waits for CI.
- Keep `main` green. If it breaks, fix forward with a new PR; do not revert someone else's work to get there unless the fix is not obvious.

## Checks

A pull request merges on its local gate: `npm ci && npm run build && npm run check`, which runs `typecheck`, `lint` and `test`. A template or release pull request also runs `npm run templates:check`.

CI (`.github/workflows/ci.yml`) runs the same on every pull request and on `main`, but nobody waits for it before merging. Watch `main` anyway: when its `check` goes red, fix it forward at once.

The workflows in `.github/workflows/` are rendered, not written by hand: each is declared in TypeScript in `.github/src/<name>.ts` with `@intentius/chant-lexicon-github`. Edit the declaration, run `npm run workflows`, and commit both; `npm run check` fails when a rendered file differs from its declaration (`test/workflows.test.ts`).

## Claims and the bench are not part of development

The scenario claims (`npm run claims`, `scenarios/`) and the bench (`npm run bench`) run between development cycles, when a person starts them. Nothing merges or releases on them, and nobody waits on them. A coding agent never runs them: both refuse to start without a real terminal, and ask a person to type `run`. `.github/workflows/claims.yml` and `claims-weekly.yml` (the published package) run only when started by hand. A change that needs a new claim part writes it; a person runs it with the next cycle's claims.

## chant

- `@intentius/chant` and `@intentius/chant-lexicon-sql` come from npm. Never a `file:` or workspace link in `package.json`.
- A PR that needs a chant change waits until that change is released on npm. Develop against a packed (`npm pack`) or linked chant in the meantime, but never merge a PR that depends on one.

## The emulator

- Start it with `chant emulator up --lexicon sql`. It is shared: do not stop or restart it while someone else may be using it.
- Write only to your own ClickHouse database or Postgres schema, named `yodel_<issue>` (for example `yodel_8`).
- A local Postgres holds `127.0.0.1:5432`, so `localhost` does not reach the emulator. Use the machine's LAN address (`ipconfig getifaddr en0` on macOS) or the stack's Docker network.

## Other tools

The docs, READMEs and issues describe what SQL Yodeler does. They do not compare it with other migration tools, and nobody benchmarks another tool's binary from this repository.

## Releasing

`@intentius/sql-yodeler` is published to npm by `.github/workflows/publish.yml` when a `v<version>` tag is pushed. Nobody runs `npm publish` by hand. The workflow checks that the tag matches `package.json`, runs `npm ci`, `build` and `check`, and publishes with npm trusted publishing: npm trusts the workflow by its file name, `publish.yml`, so there is no npm token, and renaming the file breaks publishing until the trusted publisher on npmjs.com is changed too. npm attaches a provenance attestation that links the release to the workflow run. After the publish, a smoke job installs `@intentius/sql-yodeler@<version>` from the registry into an empty directory, retrying until the registry serves it, and checks that `npx yodel --version` prints the version.

The image job then builds the CI image (`.github/image/Dockerfile`, declared in `.github/src/image.ts`: Node 22, yodel, chant and the sql lexicon) from that release for linux/amd64 and linux/arm64, pushes it to `ghcr.io/intentius/sql-yodeler:<version>` with provenance and an SBOM, and runs `yodel --version` from the pushed image. Nobody pushes the image by hand. The `image` job in `ci.yml` builds the same Dockerfile from `npm pack` of the pull request on every change.

A release takes two runs of `npm run release` (`scripts/release.sh`, which needs `gh` signed in):

1. `npm run release -- 0.1.1` while main's `package.json` is at an older version: it makes branch `release-0.1.1` from `origin/main` with the version bumped in `package.json` and `package-lock.json`, pushes it and opens a pull request, `chore: release 0.1.1`. That pull request follows the rules above: merged on its local gates. Move the templates' range in the same pull request when the release needs it (below).
2. Once main is at that version and the release commit's local gate passes (`npm ci && npm run build && npm run check` in a fresh worktree of that commit), `npm run release -- 0.1.1 --skip-ci --commit <sha>` tags `v0.1.1` on it and pushes the tag. `--skip-ci` (or `YODEL_RELEASE_SKIP_CI=1`) is how releases are made: it does not look at CI, and still refuses a commit that is not on main or not at 0.1.1. Without `--commit` it tags `origin/main`. Without `--skip-ci` the script tags only a commit whose `ci` push run concluded success (the newest such commit at 0.1.1, or the one `--commit` names), and says why when none does.

Run step 2 with `--dry-run` first. `--dry-run` (`-n`) runs every check and says what it would do, without making a branch, pull request or tag. The script refuses a version that is not `X.Y.Z`, a tag that already exists, a version already on npm and a version below main's.

The templates take `@intentius/sql-yodeler` with a caret range (`^0.1.0`), which in 0.x does not reach the next minor version. A minor release moves both templates' range to it in the release pull request itself; `templates:check` takes `npm pack` of the checkout until the release is on npm, and the forge claims then install the new release.

A template change that needs unreleased yodel ships with the release that has it: in the release pull request, with the templates' range moved to that release, never before. A project made with `chant init --from INTENTIUS/sql-yodeler@main#templates/<dialect>` installs the range from npm, so main's templates must work with what is published. Inside this repository nothing shows it (tsconfig.json maps `@intentius/sql-yodeler` to `./src`, and the forge claims pack this checkout), so the `check` job runs `npm run templates:check` (`scripts/templates-check.ts`): for each template it makes a project with `chant init --from`, installs the yodel the range resolves to on npm, and runs `git init`, `yodel ci --check`, `npm run typecheck`, `just up`'s `scripts/local.ts` against a throwaway server in Docker (it makes the read-only reader, and `yodel status dev` with the reader and writer it prints exits 0), `yodel new init` and `yodel lint`. When nothing on npm satisfies the range and the range's version is `package.json`'s, the pull request is the release that ships it, and the project takes `npm pack` of the checkout instead.

0.1.0 was published by hand, before this workflow, so the first release made this way is 0.1.1 or later.
